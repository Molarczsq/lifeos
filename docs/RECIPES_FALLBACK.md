# 无模型密钥时的分步菜谱降级（可选补充）

本分支相对上游 `main` 是**纯增量**改动：不删除、不重写上游已有的生成式饮食工作流、确认动作、v2 顾问编排，也不动已标记 `deprecated=True` 的兼容路由。

## 为什么补这一层

上游 `ai_services.py` 的 `Recipe` 生成完全依赖模型：未配置 `LLM_API_KEY` 或供应商不可用时，新接口按设计明确提示不可用。这对本地开发、离线演示、CI 和没有额度的场景意味着「怎么做菜」这条路径完全走不通。本补充提供一条**透明的降级路径**，让应用在没有模型时依然能给出可操作的分步做法，同时不把规则输出伪装成模型结果。

## 提供什么

- `POST /api/v1/recipes/recommend`：按手里的食材、口味、可用时间、份数与忌口，返回菜名、用料、分步做法、每步火候与火候提示。
- `backend/app/recipes.py`：6 道内置本地菜谱 + 确定性匹配（时间 / 忌口 / 口味 / 食材命中数）。
- 双模式：配置密钥且用户授权 `external_ai` 时，首选菜谱的做法由模型生成（`RecipeAnswer` JSON Schema 校验 + `review_answer` 复核），失败自动降级；其余候选始终来自本地库。
- 每条结果带 `source`：`live-model` / `local-library` / `fallback`；响应 `mode` 与 `note` 明确说明份量与营养为估计、调味料需另备、模型输出未经人工逐条核验。
- 前端「怎么做菜」入口复用现有 `saveFood`、`/meals/feedback`、`/meals/simulate`，不引入新的数据持久化。

## 与上游设计的关系

- `docs/AI_MIGRATION.md` 已决定移除静态三食谱 / 盲盒界面并把旧 API 留作兼容层。本分支**不重复删除**，避免破坏兼容契约；本地菜谱库只作为「模型不可用时的降级」，不替代上游生成式 `Recipe` 与确认后写入机制。
- 若维护者认为不需要降级能力，可只取后端接口与测试，前端入口单独取舍；各部分之间没有强耦合。

## 能力边界（如实标注）

- 菜谱步骤是一般家常做法建议，不是医疗或营养处方；份量与营养均为估计，调味料与另备食材未计入。
- 忌口只识别内置清单；未识别项会在 `note` 中提示「无法核实，请自行确认」，不保证交叉接触安全。
- 模型生成的步骤未经人工逐条核验。本次验证使用 mock provider 契约测试，**没有真实模型密钥，未验证真实模型输出**。
- 验证范围：上游全量后端测试 + 新增菜谱测试（规则模式、忌口过滤、未知忌口、mock 模型来源标注）、前端 `tsc --noEmit`、Next.js 生产构建。Playwright E2E runner 未执行。
